# Restricted MTP draft-head experiment

Measured on 2026-10-20, starting from main `cc4b6b88`, on one RTX 5090
with PyTorch 2.12.1+cu132. The target was the converted RedHatAI
Qwen3.8-27B-INT4 checkpoint, with a dense BF16 output generator.

## Method

`benchmark_draft_vocab.py` compares the unchanged full draft generator against
an additional dense head containing 40,960 of 248,320 vocabulary rows. Both arms
keep that extra allocation (400 MiB) resident, use the same loaded target,
three MTP drafts, greedy decoding, FlashAttention, packed KVQ, a 64,000-token
context limit, and a 512-token output cap. Each arm is warmed before measurement;
two measured repetitions alternate arm order. All measured outputs reached the
512-token cap. Decode throughput counts the 511 tokens after the first token,
using synchronized first-to-last-token timing. Per-phase profiling is enabled
in both arms. These are small workload samples, not a general quality evaluation.

The shortlist comes from the pinned external repository linked in the
[recipe](README.md#experimental-restricted-mtp-draft-vocabulary), SHA256
`b64b6dfcf5441eb995ddf77d3d37b018e91b88c56ad1b4c5774ad8fbfac1c388`.
It is an English/code-oriented example, not a recommended multilingual vocabulary.
The file is downloaded separately and is not bundled into Eole.

## Results

| Compile mode | Prompt | Full head tok/s | Restricted head tok/s | Change | Acceptance full → restricted |
| --- | --- | ---: | ---: | ---: | ---: |
| 0 | Orwell | 101.68 | 111.37 | +9.5% | 48.4% → 43.9% |
| 0 | Code | 144.22 | 168.28 | +16.7% | 82.3% → 82.3% |
| 0 | French | 103.85 | 93.42 | -10.0% | 49.9% → 31.8% |
| 2 | Orwell | 98.45 | 107.51 | +9.2% | 49.6% → 44.0% |
| 2 | Code | 129.95 | 151.10 | +16.3% | 80.0% → 76.7% |
| 2 | French | 95.72 | 88.86 | -7.2% | 49.5% → 30.6% |

Rates are means of the two repetitions; acceptance is accepted/drafted tokens
aggregated across those repetitions. Different text trajectories can change
acceptance and speed, so only the code comparison in mode 0 also holds generated
text identical between arms.

The isolated draft projection plus argmax measured 1.662 ms with the full
head and 0.263 ms with the shortlist (6.3× faster),
averaged over 100 GPU-event-timed calls after 10 warm calls in the clean mode 2
process. This excludes the MTP transformer and target verification.

## Correctness and limitations

Only draft proposals use the smaller head. Target verification, its full output
vocabulary, target weights and normalization are unchanged. Excluded tokens can
still be generated by the target. The implementation supports dense `nn.Linear`
output generators and rejects other types. Tensor parallelism has not been
benchmarked for this experiment.

Mode 0 code outputs were identical between arms and repeats. Prose outputs were
stable within each arm but differed across arms. A separate instrumented target
trace found that both first divergences involved a target-score tie in the
full-head run:

| Prompt | Generated-sequence position including prompt | Full-head target top two log probabilities | Restricted-head target top two log probabilities |
| --- | ---: | --- | --- |
| Orwell | 350 | -1.1796875, -1.1796875 | -1.1328125, -1.2578125 |
| French | 454 | -0.75, -0.75 | -0.6875, -0.8125 |

This is consistent with BF16 numerical differences when changed proposals alter
verification chunk boundaries. It is not evidence that target verification was
restricted, nor a guarantee of bitwise-identical greedy output. Target-tie
sensitivity already matters for MTP, and the shortlist adds another way to change
the verification grouping.

The French acceptance loss is the key tradeoff: cheaper draft projection can
be outweighed by more verification cycles. Keep this opt-in and measure a
shortlist on the intended workload before deploying it.
