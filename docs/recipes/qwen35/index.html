Qwen3.5: text, vision, streaming, and serving

Run from the repository root. Follow the installation guide for Eole CUDA kernels, FlashAttention, and fla-core in your CUDA-enabled environment. The inference scripts use Qwen/Qwen3.5-4B; the server example uses a separate 27B INT4 checkpoint. These are different model paths, not interchangeable steps.

Convert and run the 4B examples​

export EOLE_MODEL_DIR="$PWD/models"
mkdir -p "$EOLE_MODEL_DIR"
eole convert HF --model_dir Qwen/Qwen3.5-4B \
  --output "$EOLE_MODEL_DIR/qwen3.5-4B"

The scripts select FlashAttention; install flash-attn --no-build-isolation, or change self_attn_backend="flash" to "pytorch" to use the fallback backend.

python recipes/qwen35/test_inference.py   # image questions with bundled fixtures
python recipes/qwen35/test_inference2.py  # text generation
python recipes/qwen35/test_stream.py      # live text streaming

The first script prints one response per image in eole/tests/data/images. The second prints a generated passage. Adjust GPU ranks, generation length, and model paths in the scripts to fit your hardware.

For a small text fine-tuning run, see Qwen LoRA.

Serve a model​

For the small-model starting point, use the server recipe. serve.yaml in this directory is an advanced Qwen3.5-27B INT4 example: it requires a converted checkpoint at $EOLE_MODEL_DIR/qwen3.5-27B-int4, quantization kernels, and FlashAttention. Its large context/cache settings must be adjusted to available VRAM; it is not a conversion or download recipe.

eole serve -c recipes/qwen35/serve.yaml --host 127.0.0.1

For Qwen3.8 MTP and a reproducible baseline comparison, use the Qwen3.8 recipe.

MoE execution and the CPU/GPU prototype​

moe_expert_backend: resident remains the default. It uses the existing fused GPU expert kernels, with the same checkpoint keys and routing mathematics. Expert kernel caches/dispatch now live in eole/modules/expert_execution.py; MoE retains routing and shared-expert behavior. The loader asks a separate placement policy where each module belongs instead of tying placement to the checkpoint reader.

Adaptive INT4/INT8 GPU cache​

moe_expert_backend: adaptive uses one bounded GPU expert cache with two explicit weight paths:

Converted source checkpointCPU expertsGPU expertsWeight changes
GPTQ INT4Original INT4Original INT4 (Marlin)Codes/scales preserved
Floating-point (BF16/FP16)Runtime INT8Same runtime INT8 (Marlin)Per-output-channel RTN quantization

The floating-point path quantizes routed experts once at load. CPU and GPU share the same signed INT8 codes and rounded BF16 scales; changing residency does not change quantization. The GPU repeats each per-channel scale across 128-value groups to use the existing Marlin group layout. Attention, shared experts, vocabulary heads and FP32 normalization retain their existing precision. Runtime quantization changes numerical behavior versus the floating-point checkpoint.

The existing hybrid_int8 backend remains the fixed CPU INT8/GPU BF16 variant. hybrid_gptq remains an alias restricted to GPTQ INT4; use adaptive for either supported source. Loading an already-quantized GPTQ INT8 checkpoint is not yet supported. GPTQ inputs require symmetric INT4, group128, BF16 scales, direct zero point 8, no activation ordering or bias; unsupported layouts are rejected.

The floating-point source path requires Eole's BF16-activation INT8 MoE CUDA specializations. If your installed extension predates this support, rebuild it from the repository root with the intended Python environment active:

MAX_JOBS=4 python setup.py build_ext --inplace
CUDA_VISIBLE_DEVICES=0 OMP_NUM_THREADS=6 MKL_NUM_THREADS=6 EOLE_TORCH_COMPILE=0 \
  python recipes/qwen35/benchmark_moe.py \
  --model /path/to/converted/Qwen3.5-35B-A3B-GPTQ-Int4 \
  --backend adaptive --gpu-experts 64 --cache-policy frequency \
  --cache-dir /path/to/local/ssd/cache \
  --tokens 128 --repeats 3 --output /tmp/qwen35-adaptive.json

For a floating-point source, set QWEN35_MOE_MODEL and use predict-adaptive.yaml. For GPTQ INT4, set QWEN35_MOE_GPTQ_MODEL and use predict-hybrid-gptq.yaml. Equivalent inference settings:

moe_expert_backend: adaptive
moe_gpu_experts: 64
moe_expert_cache_policy: frequency  # fixed keeps the initial residency
moe_expert_cache_interval: 32
moe_expert_cache_swaps: 4
moe_expert_cache_dir: /path/to/local/ssd/cache
moe_expert_cuda_graph: true
compute_dtype: bf16
self_attn_backend: flash
dynamic_shapes: false
self_speculative_decoding: false

The slot count is per layer, not a VRAM limit. Leave room for dense weights, KV/recurrent state, graph pools, prefill workspace and one spare expert per layer. Start conservatively and measure process GPU memory with your intended context and prompts. Increasing batch size or context changes the required headroom.

Frequency admission learns demand over successive requests, replaces at most four experts every 32 layer calls, and decays old counts. It changes residency only: every selected expert is still evaluated with its original routing weight. Cache misses run on the CPU while cached experts run on the GPU. A frozen domain-specific cache can be faster than adaptation for a stable workload; changing domains needs time to learn. No policy guarantees that adaptation improves every request.

GPU execution uses Eole's existing Marlin kernels. Single-token expert graphs use a persistent GPU ID-to-slot table; supported decoder layers also capture attention, routing and shared-expert stages around the CPU handoff. Prefill and unsupported layer layouts stay eager. Static KV/GDN buffers are owned by the hybrid runtime and reset in place at the next request. Compatible requests reuse their graphs; a batch/shape/dtype/device change invalidates the bindings before buffers are replaced. The first two real decode calls warm a new stage and the third captures it. Initial capture costs remain part of the first request's latency. Attention/routing and shared-expert stages share one ordered CUDA graph pool; expert graphs keep their own pools. All participating stages warm up before capture starts, and replay follows the model's layer order on one stream. Changing a captured signature or interrupting a cycle abandons that pool until the next request. Graphs are released before replacing cache buffers or closing the expert runtime.

Runtime dense/head quantization finishes before GPU expert banks are allocated. This reduces startup peaks and leaves more VRAM available for expert slots. These changes do not select a larger moe_gpu_experts automatically: retune that setting against measured peak memory. The ordinary resident backend and expert routing/quantization are unchanged. --no-hybrid-graph disables all these hybrid GPU stages for comparison. When every expert fits in the cache, no CPU routing readback or CPU expert job is needed. This does not enable whole-decoder torch.compile: the backend still requires EOLE_TORCH_COMPILE=0, one GPU and ordinary decoding.

CPU native INT4/INT8 layouts stay in RAM. Separate Marlin layouts are temporarily memory-mapped on the selected SSD, so they do not require a second anonymous RAM bank. Allow disk space for the routed expert weights at execution precision (INT4 or INT8). Preparation can take minutes and is excluded from decode timings. Packing occurs at model load, one expert at a time on CUDA. Temporary files are removed when the engine is terminated or preparation fails. This is an in-process GPU cache, not an SSD-streaming inference engine or a reusable converted checkpoint format. CPU/GPU kernel rounding can differ near ties; this is not a promise of bit-identical generation to the fully resident backend. FP32 normalization is unchanged.

Floating-point and GPTQ path confirmation​

Both formats were rerun after adding INT8 MoE kernels: eight selected experts, native vocabulary head, no MTP, 4096-token context, prefill chunk 32 and 128 output tokens (127 timed), six CPU threads on the RTX 5090/Ryzen 5900X. Identical token histories are forced; these are practical checkpoint configurations, not an accuracy evaluation or an isolated expert-bitwidth ablation. Non-expert weights retain each source checkpoint's precision. Unused vision modules were on CPU.

BF16 source with CPU INT8​

moe_expert_backend: hybrid_int8 is an experimental capacity-oriented path:

  • Start from an unquantized converted checkpoint, not the GPTQ/NF4 checkpoint.
  • The first moe_gpu_experts experts in each layer stay on CUDA in BF16. Remaining experts stay on the CPU during loading and are packed to per-channel INT8 weights. Source weights are released expert by expert; they are not staged through CUDA. CPU activations are BF16 using PyTorch's native CPU matrix kernel.
  • All selected experts are evaluated. CPU and GPU results are merged in routed order with the original weights; no experts are pruned or skipped. Runtime weight quantization changes numerical results compared with the BF16 source.
  • One shared CPU worker overlaps CPU expert work with resident GPU experts. This is a fixed partition, not an adaptive expert cache or SSD-offload engine.
  • Currently requires one CUDA GPU, BF16 compute, gated-SiLU experts, ordinary decoding and EOLE_TORCH_COMPILE=0. MTP, DFlash2, tensor parallelism and whole decoder compilation is rejected for this backend. The default resident backend keeps its existing capabilities. No new extension build or dependency is needed.

Use a checkpoint converted with current Eole (older Qwen conversions may still have an incorrect RoPE layout). For example:

export QWEN35_MOE_MODEL=/path/to/converted/qwen3.5-35B-A3B
CUDA_VISIBLE_DEVICES=1 OMP_NUM_THREADS=6 MKL_NUM_THREADS=6 EOLE_TORCH_COMPILE=0 \
  python recipes/qwen35/benchmark_moe.py \
  --model "$QWEN35_MOE_MODEL" --backend hybrid_int8 --gpu-experts 64 \
  --tokens 64 --repeats 3 --output /tmp/qwen35-hybrid.json

Alternatively use predict-hybrid.yaml, whose conservative 16-expert default uses less VRAM. This is a count per layer, not a memory budget; choose it for the checkpoint and available VRAM. CPU thread settings are explicit process settings; Eole does not change global thread counts. Keep the original checkpoint for reload/training; the CPU packs are inference-only runtime state.

The near-identical resident eager speeds suggest host launch/synchronization overhead limits GPU scaling; compiled execution exposes the hardware difference. It does not establish which individual operations cause the eager overhead.

Lightweight host timing of three additional hybrid runs on the 5090 measured 62.8 ms/decode token overall. CPU expert work took 22.6 ms/token, including 15.2 ms/token in native CPU linear calls. Whole-decoder compilation is currently rejected by this prototype; compiling GPU segments around the host-execution boundary is a possible next experiment.

GPU stages around the host expert boundary​

For hybrid_int8, moe_expert_cuda_graph: true (default) captures two GPU phases per supported decoder layer: attention/normalization/routing, then the shared expert and residual combination. CPU expert execution and the existing resident-expert dispatch remain outside these graphs. This does not compile the whole decoder or change expert selection, quantization or FP32 normalization.

The graph path requires ordinary single-token inference, a static cache (dynamic_shapes: false), FlashAttention and the supported sequential residual layout. Prefill, batches larger than one, attention/alignment output and other unsupported layouts retain the eager path. The first two eligible calls run eagerly; the third captures and executes once. Compatible requests reset owned KV/GDN buffers in place and reuse the captures. A changed cache shape, dtype or device invalidates the graphs before replacing their buffers. Termination releases the graphs and CPU worker; a capture failure warns and falls back.

To compare the same backend without these GPU graphs, set moe_expert_cuda_graph: false or pass --no-hybrid-graph to benchmark_moe.py. Whole-decoder EOLE_TORCH_COMPILE remains disabled.

The CPU single-token worker also avoids regrouping already-distinct top-k expert IDs and redundant input copies. Multi-token prefill retains grouped expert execution and the original route ordering.

Runtime INT8 dense projections​

dense_quantization: int8 optionally quantizes the remaining native FP16/BF16 decoder attention and MLP projections at model initialization. This is useful with a GPTQ INT4 MoE checkpoint: routed experts keep their calibrated checkpoint weights, while native attention and shared-expert projections use symmetric round-to-nearest INT8 with group size 32 and FP16/BF16 activations. It also works with adaptive expert placement; the expert backend keeps its separate policy.

# Add to a prediction config, or the model's config section in a server YAML.
dense_quantization: int8        # default: none
fuse_kvq: true
fuse_gate: true
vocabulary_quantization: int8   # independent; none/int8/int4

This currently requires single-GPU CUDA inference with the Eole Marlin extension. Only native, bias-free projections with input dimensions divisible by 128 and output dimensions divisible by 64 are converted; unsupported projections remain native with a warning. Already quantized projections, routed experts, routers, GDN A/B controls, normalization, embeddings, vision components and vocabulary heads are excluded. Separate MTP/drafter modules are also left unchanged. fuse_kvq and fuse_gate use the existing packing paths, including shared-expert gate/up packing. Activations retain the compute dtype; this does not enable INT8 activation quantization.

Quantization occurs once per model load, before compilation and warmup, without modifying checkpoint files. It adds initialization work and changes numerical results; it is not a lossless transformation. The default remains none.

For a local comparison, run the same command with --dense-quantization none and --dense-quantization int8, keeping the vocabulary quantization and expert backend unchanged. For example:

EOLE_TORCH_COMPILE=1 EOLE_COMPILE_MODE=0 \
python recipes/qwen35/benchmark_moe.py \
  --model "$QWEN35_GPTQ_MODEL" --backend resident --task code \
  --dense-quantization int8 --vocabulary-quantization int8 \
  --output /tmp/qwen35-dense-int8.json

For adaptive mode, use EOLE_TORCH_COMPILE=0, --backend adaptive, and the same --gpu-experts value for both runs. This benchmark generates freely: quantization can change the output, expert routing and EOS position, so compare several tasks and inspect the recorded output lengths as well as throughput.

Dynamic INT8 activations (W8A8)​

Use dense_quantization: w8a8 instead of int8 to additionally quantize the selected projections' activations dynamically, in groups of 32. This requires the rebuilt Eole CUDA extension on a single NVIDIA GPU. Small-row INT8 projections and activation rounding use CUDA DP4A kernels. The vocabulary head, routed experts, routers, normalization and separate MTP/drafter modules keep their independent precision settings.

Weights use the same RTN INT8 codes and rounded scales as int8. Only one weight layout is retained, including after fuse_kvq / fuse_gate packing. For batches below 64 rows, DP4A integer dot products use identical per-row arithmetic for ordinary decoding and verification. Larger prefills use the same activation quantization, round its dequantized values to the compute dtype, and execute Marlin with a temporary repacked weight layout. That layout is released after the call, rather than keeping a second model-sized weight copy. Prefill therefore has an additional conversion cost, and its floating-point rounding can differ from the small-row path. Both FP16 and BF16 compute are supported.

This is an opt-in accuracy/performance trade-off: activation quantization can change predictions beyond weight-only INT8. It is not a lossless optimization or a guarantee of higher throughput for every workload. The default remains none; int8 retains the existing weight-only Marlin path.

The benchmark accepts --dense-quantization w8a8. Keep vocabulary quantization, expert placement, prompts and generation settings fixed when comparing modes.

Changing this setting requires a model reload and warmup. Small-row MTP verification is covered by CUDA tests, but W8A8 is not necessarily faster with MTP, and whole-model floating-point execution is not guaranteed bit-identical between ordinary and chunked verification paths. Benchmark the intended request length and speculation settings before choosing it.
