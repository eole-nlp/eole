Continuous Responses serving

Serve multiple greedy text sessions through /v1/responses on one GPU with one model. The Codex recipe covers client setup. The load tests here use synthetic tool calls and report serving performance.

Run locally​

From the repository root, use a dedicated CUDA GPU and a converted or pre-converted Qwen3.8-27B INT4 checkpoint. The example uses greedy text requests through /v1/responses.

export EOLE_MODEL_DIR="$PWD/models"  # or your existing model directory
export QWEN38_MODEL="$EOLE_MODEL_DIR/Qwen3.8-27B-INT4"
export CUDA_VISIBLE_DEVICES=0
export EOLE_TORCH_COMPILE=1 EOLE_COMPILE_MODE=0
export TRITON_DEFAULT_FP_FUSION=1

eole serve -c recipes/serving/serve_continuous.yaml \
  --host 127.0.0.1 --port 5019

After the server reports readiness, run a text, streaming, and tool-call smoke test from a second terminal:

python recipes/codex/smoke_test.py --base-url http://127.0.0.1:5019/v1 \
  --model qwen3.8-27B

Measure latency and throughput​

Install aiohttp in the benchmark environment. Use the same prompts and request settings for each server profile:

  • recipes/serving/serve.yaml runs the serialized baseline.
  • recipes/serving/serve_continuous.yaml runs continuous greedy decoding.
  • recipes/serving/serve_continuous_mtp.yaml runs continuous MTP with three drafts.

To change profiles, stop the current server with Ctrl+C and rerun eole serve with the selected YAML and the same host and port. Then run:

python recipes/serving/benchmark_responses.py \
  --concurrency 1 2 4 8 --repeats 2 --max-tokens 128 \
  --output /tmp/eole-short.json

python recipes/serving/benchmark_agentic.py \
  --concurrency 1 2 4 8 --duration 30 --context-lines 120 \
  --tool-rounds 3 --max-tokens 128 --output /tmp/eole-agentic.json

Both scripts default to http://127.0.0.1:5019/v1, model qwen3.8-27B and a 600-second HTTP timeout. For authentication use --api-key-env NAME; its value is not saved. Stop the server with Ctrl+C to release its GPU model.

Batched MTP​

self_speculative_decoding: true selects recurrent Qwen MTP for the continuous backend; self_speculative_num_tokens sets the draft count. There is no second serving flag. The supplied MTP YAML uses three drafts and a native BF16 vocabulary head. This requires exactly one recurrent Qwen MTP head, CUDA FlashAttention, fixed-capacity one-dimensional RoPE, greedy text and one GPU.

Preparation compiles and captures the fixed-width verifier and recurrent drafter before readiness, for both the full slot bank and singleton rows. The verifier uses the same local artifact cache as standalone MTP, with separate entries for the continuous verifier's singleton and bank layouts. The cache follows speculative_verifier_cache and EOLE_VERIFIER_CACHE_DIR. Startup loads compatible artifacts and captures fresh CUDA graphs for the current process before serving requests. Each request owns its target KV/GDN state, MTP KV prefix and pending verified context. Acceptance and EOS/output-budget truncation happen independently per row. A grouped replay commits only each row's accepted GDN prefix; cancellation and slot reuse discard that request's state. Extra physical KV slots are verifier scratch and do not reduce the configured context budget. The standalone MTP drafting loop is unchanged.

The target validates every proposed token. BF16 batched/multi-token kernels can round differently from single-token decoding, including near-tie argmax changes; this does not promise bit-identical output or establish a quality score.

With eole_metrics: true, terminal responses additionally report proposed and accepted draft counts, acceptance by draft position and verifier cycles. Acceptance is accepted emitted drafts divided by all computed proposals, including proposals discarded at an EOS/output boundary. Benchmark summaries pool counts across requests rather than averaging individual acceptance percentages.

Batched DFlash2​

For a dedicated continuous server with a compatible DFlash2 checkpoint, set dflash2_model in the model config. The drafter checkpoint sets the block size. Use compiled mode 0 for the drafter bank graph. Once two or more requests are decoding, the bank drafts each slot in one replay, with independent positions and committed feature counts. A single active request keeps the singleton graph. Both graphs share the slot's ring storage, so requests can move between the two paths as other jobs arrive and finish.

Continuous prompt prefix reuse​

Set continuous.prefix_cache_entries to a positive count to retain that many prefilled prompt states with ordinary greedy decoding, MTP, or DFlash2. Use it on a dedicated server for trusted clients because cache hits can change request timing across clients. The default is zero. A hit requires the complete saved prompt to match a strict prefix of the new prompt. The matching entry moves to the new request, which prefills only the suffix. Each retained entry holds one full-capacity target KV and GDN cache plus MTP prefix KV and the last target hidden state, or DFlash2 trailing features, when enabled. Set the count with that VRAM cost in mind. With eole_metrics: true, reused_prefix_tokens reports the skipped input tokens.

What each metric measures​

The scripts request the Eole-specific eole_metrics: true extension. Terminal Responses then contain server-measured decode durations and counts; default Responses payloads remain unchanged. A mismatched old server or missing timings fails the benchmark. Model token counts and timestamps include terminal EOS when generated.

  • Per-request decode p50: the median token-delivery rate across individual model requests, including tool-call and final-answer requests in multi-turn workloads. Each rate is (generated tokens - 1) / (last server token time - first server token time). It excludes that request's initial queue/prefill and first token, but includes pauses while other requests are prefilled or decoded. It describes typical token delivery under load, not isolated decoder capacity. Serialized requests can decode quickly after a long wait; continuous requests share the GPU and can finish whole workflows sooner despite slower delivery. Percentiles use the nearest-rank convention; p10 and individual records are saved.
  • First visible output p95: client HTTP submission to first text/reasoning or tool-argument delta. This includes queue/prefill/delivery; tool blocks are buffered, so it is not pure first-model-token or prefill latency.
  • Jobs/min: complete workflows finished per minute across all clients; higher is better. Wall time includes queueing, all prefills, generation, simulated tool delays, HTTP delivery and final drain. A short-text job is one request, a short-tool job is a tool call followed by an answer, and a multi-turn or 12K-input job is three model/tool exchanges followed by a final answer.
  • Job p95: the completion time within which 95% of measured jobs finished, from each job's submission through its final response. Lower is better. For example, 31.60 seconds means 95% finished within about 32 seconds. Small samples do not establish production latency guarantees.

Combined decode-window throughput is omitted from comparisons: interleaved prefills enter the active windows in continuous mode but are outside them in serialized mode, so that metric does not isolate decoder capacity consistently.

JSON additionally retains end_to_end_output_tokens_per_second, explicitly named as such. It is not decode speed and is not shown as the headline tok/s metric. Earlier figures such as 270 short-prompt or 43 agent-loop tok/s used that end-to-end definition; they must not be read as decode-only results. Inter-chunk gaps are also not per-token latency: a tool call may arrive in one SSE event. Server timings avoid that buffering error.

Retained sustained reuse/cancellation check​

The earlier four-slot/eight-client, 8K-context soak used 256 active / 512 idle. A 180-second admission window plus drain took 200.58 seconds: 47 jobs / 188 ordinary requests / nine intentional disconnects, or 14.06 jobs/min. All tool/protocol checks passed; no ordinary response hit its cap. Clients completed 6, 6, 6, 6, 6, 6, 6, 5 jobs; short/long first-visible-output p95 was 7.98 / 8.32 seconds and overall job p95 was 37.48 seconds.

Reproduce with benchmark_agentic.py --concurrency 8 --duration 180, using an 8K YAML copy. This reliability run need not be repeated to relabel its metrics.

Worker ownership and supported settings​

One dedicated worker owns the engine. RequestCache transfers ownership of KV, GDN recurrent/convolution state, padding and positions; admission copies a separately prefilled request into its slot once. Singleton row views share bank storage. Explicit decoder steps use per-row RoPE positions; ordinary predictor routing retains its existing path. Startup prepares bank/singleton graphs before readiness; failed capture fails preparation. Shutdown stops the worker, closes graphs and unloads the model. A worker failure fails affected streams and requires reload. Queued, prefilling and decoding cancellation retire/release capacity.

Only greedy text Responses are supported. Sampling, penalties, images, Non-recurrent MTP variants, tensor parallelism and general prediction/scoring are rejected. Use temperature: 0 or greedy defaults. The server must contain one model and must not use model_policy: single, whose lease would serialize it. Another ordinary predictor must not run on the worker-owned engine concurrently.

The core probe below tests late arrivals, mixed lengths, cancellation and reuse. It reports actual chunk boundaries, widths, tokens and mismatch diagnostics:

CUDA_VISIBLE_DEVICES=0 EOLE_TORCH_COMPILE=0 \
python recipes/serving/check_continuous.py --model "$QWEN38_MODEL" \
  --output /tmp/eole-continuous-core.json

Correctness: solo bit-identity is not guaranteed​

The earlier 92-token check was too small to support a broad equality claim. The expanded test ran ten requests, cancelled three in queued/prefill/decode states, and completed seven for 1,558 generated tokens. All references replay the request's actual prefill chunks.

  • Against compiled single-row free generation, four of seven continuations diverged, first at token indices 67, 147, 177 and 64 (zero-based). Against an eager singleton reference, first divergences also differed. Thus selecting matching compilation alone does not ensure cross-batch identical output.
  • At the first compiled-solo divergences, final-hidden relative RMS differences were roughly 0.7–1.2%; each decision involved the same two leading candidates, with rounded log-probability ties in one path. This is evidence consistent with width-dependent numerical differences, not a model-quality measurement.
  • A separate state-isolation control replayed the actual token prefixes with the same slot, batch width and prefill boundaries, but removed other live requests. All 1,558 target decisions matched. This checks isolation under matching arithmetic; it is not independent single-row free generation and does not prove universal absence of state bugs.

The probe records widths, tokens and first-mismatch diagnostics. By default a mismatch fails the run. --allow-divergence explicitly permits saving a numerical comparison without a failing exit; do not treat that flag as an equality pass.

# Cross-batch comparison: numerical divergence can occur.
EOLE_TORCH_COMPILE=1 EOLE_COMPILE_MODE=0 \
python recipes/serving/check_continuous.py --compiled-step --slots 4 --tokens 256 \
  --prefill-idle-chunk-size 512 --allow-divergence \
  --model "$QWEN38_MODEL" --output /tmp/eole-solo-comparison.json

# Strict isolated-state comparison with matching arithmetic schedule.
EOLE_TORCH_COMPILE=1 EOLE_COMPILE_MODE=0 \
python recipes/serving/check_continuous.py --compiled-step --reference-mode isolation \
  --slots 4 --tokens 256 --prefill-idle-chunk-size 512 \
  --model "$QWEN38_MODEL" --output /tmp/eole-state-isolation.json

The uniform-table RoPE regressions compare legacy 2-D and repeated 3-D tables for multiple rows and tokens, in CUDA FP16/BF16 and the PyTorch/compiled-dispatch branch. Greedy selection still uses the existing log_softmax().argmax() rule: removing log-softmax is mathematically valid but can change decisions through low-precision rounding/ties, so it is not folded into this serving change. Tokenization remains on the worker and decisions still synchronize with the CPU once per tick; those remain profiling opportunities.

The qualified workload here is single-GPU greedy text Responses serving on the measured RTX 5090 configurations. Larger contexts, other hardware and actual Codex coding-task quality remain outside this qualification. No native Eole extension rebuild is required; startup still prepares runtime-specific torch.compile programs and CUDA graphs.

Automated GPU correctness tests​

eole.tests.test_continuous_gpu uses small, explicitly initialized Eole decoders with real FlashAttention and FLA kernels, not a fake runner or downloaded weights. Both attention-only and GDN models compare mixed-position batched logits and KV/recurrent/convolution state against independent ordinary decoding with BF16 tolerances. Tests exercise admission into occupied rows, late arrivals, partial prefill cancellation, slot reuse, compiled replay and the inference-mode contract. The MTP suite additionally checks recurrent drafts against standalone MTP, different per-row GDN commit lengths, EOS, context boundaries, cancellation and reuse with compiled verification. CPU tests compare grouped commits to independent sequential prefixes and check convolution history across prefill chunks. The random-weight scheduler fixture also checks its emitted tokens against solo inference; this does not assert universal bit-identity on arbitrary checkpoints.

CUDA_VISIBLE_DEVICES=0 EOLE_TORCH_COMPILE=1 EOLE_COMPILE_MODE=0 \
EOLE_REQUIRE_GPU_TESTS=1 python -m unittest -v \
  eole.tests.test_continuous_gpu \
  eole.tests.test_continuous_mtp_gpu \
  eole.tests.test_request_cache.RequestRotaryCudaTests

This requires matching Eole CUDA ops, FlashAttention and FLA in the environment. EOLE_REQUIRE_GPU_TESTS=1 fails if CUDA or the required compile configuration is missing, rather than allowing the GPU job to pass with skipped tests. Ordinary CPU CI still skips the CUDA integration cases.

The Continuous decoder GPU tests Actions workflow is prepared for a self-hosted Linux x64 runner labelled gpu, with a compatible Torch/FlashAttention/FLA Python environment and CUDA toolkit. It builds this checkout's ops in an isolated venv for the attached GPU. No GPU runner is currently configured: the tests have run locally, and GPU CI is not yet an active check. After registering that runner, maintainers can dispatch reviewed refs manually. Set the repository Actions variable EOLE_GPU_CI=true to enable automatic same-repository PR runs. Fork code never runs automatically on the self-hosted host; manual dispatch is for reviewed code only. The workflow must be available on the default branch before dispatch.

Runtime contracts​

Compilation keeps normal Dynamo guards. Captured CUDA graphs require model flags, parameter/cache storage and layouts to remain fixed for the worker lifetime; change model configuration through unload/reload, not mutation during replay. The bank still runs all rows when at least two requests are active. Idle-row cost is a documented trade-off; per-step KV gathering/compaction is outside this change.

Requests with 0 < top_p < 1 are rejected; 0 disables nucleus filtering and 1 keeps the full distribution before greedy selection. Admission requires exactly one nonempty unpadded source sequence, checked against the collator's srclen. Formatted prompt EOS/turn-boundary IDs remain valid. Other generation routes, including Chat, Anthropic, native inference and workspace POST routes, return a clear 409 before model loading or SSE headers on a continuous-only server.

Cooperative cancellation cannot interrupt a hard-hung CUDA kernel. The worker must retain ownership of state while it runs; a timeout must not release that state for another request. A hard device hang requires an external process supervisor to restart the server. There is no in-process CUDA-hang recovery here.

FP8 target KV cache​

Set kv_cache_dtype: fp8_e4m3 in the model's continuous settings to store the target attention cache in E4M3 on CUDA compute capability 8.9 or newer. For example, add this inside the model's continuous block:

continuous:
  slots: 1
  kv_cache_dtype: fp8_e4m3

Set the KV dtype and scales in the continuous block for continuous serving. The default native keeps the model's compute dtype and rejects a conflicting FP8 setting in the model's ordinary inference config. FP8 requires a working FlashAttention backend, with FlashInfer installed for prompt prefill and a length-aware Triton split-KV kernel for decode and verification. The CUDA tests use FlashInfer 0.7.2. This path requires full-window attention, head dimension 64, 128 or 256, and verification blocks of up to 16 tokens.

An optional kv_cache_scales list contains a [key_scale, value_scale] pair for each decoder layer. Use null for GDN layers. Omitted scales default to one. Start with unit scales and evaluate calibrated scales on held-out prompts before deploying them. The cache stores values divided by their scales and uses the corresponding scales on reads. Target K/V storage is halved. GDN and drafter state retain their existing dtype, and split attention uses temporary reduction buffers. Leave room for prefill activations and CUDA graphs when choosing the number of slots and context capacity. A cache can fit at startup while a long prompt still runs out of VRAM.
