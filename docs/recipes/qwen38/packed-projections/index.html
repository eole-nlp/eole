Packed Marlin projections

fuse_gate: true packs compatible Marlin MLP gate/up projections. fuse_kvq: true also packs compatible GDN QKV/Z projections, in addition to attention KVQ. Both options default to false. Packing happens during inference preparation, before Marlin weight repacking; incompatible pairs retain separate projections with a warning. MoE expert stacking keeps its existing initialization path.

The paired BF16 GDN A/B kernel now handles one-token decoding automatically, as well as four-token MTP verification. Its specialized path requires a single GPU, batch/beam size one, BF16 inputs, and the supported 5120-to-96 shape on Ampere or newer. Other configurations retain their existing projection path. The prepared A/B buffers use about 47 MB across 48 GDN layers.

No checkpoint conversion or native-extension rebuild is required. The feature uses existing Marlin kernels and a lazily compiled Triton one-token kernel. FP32 normalization and BF16 vocabulary heads remain unchanged. This change does not include cache-view, recurrent-state commit, or vocabulary quantization work.

Reproduce​

CUDA_VISIBLE_DEVICES=0 EOLE_TORCH_COMPILE=1 EOLE_COMPILE_MODE=0 \
  python recipes/qwen38/benchmark_marlin.py \
  --model "$QWEN38_MODEL" --fuse-gate --output /tmp/packed-no-mtp.json

Add --mtp for three-draft MTP. Omit --fuse-gate to keep gate/up separate. --no-fuse-kvq disables attention KVQ and GDN QKV/Z packing; the automatic paired A/B dispatch is independent of that flag.

Validation​

CPU coverage includes inference wiring, incompatible-pair fallback, missing configuration fields, dense fusion and MoE initialization. CUDA coverage checks packed projection outputs, compiled execution, changing-input graph replay, and the paired A/B kernel against FP64 references on RTX 5090 and RTX 4090. Short compile-mode-2 runs cover ordinary decoding and MTP; these are compatibility checks rather than throughput comparisons with the mode-0 measurements above.

The CPU suite passed 752 tests (39 skipped). The focused CUDA suite passed 32 tests on each GPU, including INT4/INT8 packed projections in FP16 and BF16. Full-model compiled smoke runs passed for batch four, beam four, worker-thread streaming, MTP sampling, and two-GPU tensor parallel (RTX 5090 + RTX 4090), with both fusion flags enabled. These smoke checks establish execution compatibility, not throughput gains for those configurations.

Fusion setup memory​

Fusion now finalizes deferred Marlin weights layer by layer and returns unused CUDA allocator blocks after each affected layer. Original projection modules are deleted when replaced; this also avoids accumulating cached temporary concatenation/repacking allocations. Cache release occurs only during setup, not during inference.

On the same RTX 5090 checkpoint with both flags enabled, a fresh-process setup comparison measured the following (MiB, PyTorch allocator counters):

Live weights after fusion remain about 18756 MiB. Model build/load took 5.86 s before and 5.73 s after in this check; these single measurements are not a startup-speed benchmark. These figures cover projection preparation, not later KV caches or compilation/CUDA-graph memory. A regression test checks that the first layer's original modules have been freed and its packed projections initialized before the next layer is fused.

After the memory follow-up, the CPU suite passed 753 tests (39 skipped), the focused suite passed 33 tests on each GPU, and a real compiled MTP-sampling request passed with both flags enabled.

Full-request cache memory​

A follow-up using recipes/qwen35/test_inference3.py settings (64k context, 4096 output cap, MTP disabled, compile mode 0, both fusion flags enabled) found two avoidable full-cache allocations: reinitializing caches after warmup, and replicating them once for a single decoding path. Compatible K/V buffers now reset in place after graph bindings are invalidated; single-path tiling returns the existing tensor. Changed batch shape/dtype/device still allocates suitable storage, and multiple decoding paths still replicate their state.

With these changes the full-run peak reserved memory fell from 27344 MiB to 23208 MiB; peak allocated memory fell from 27107.88 MiB to 22959.34 MiB. These settings reserve 2000 MiB each for keys and values, even for the short Orwell prompt. Delivered decode throughput remained 81.2 tok/s in the follow-up run. This is a memory comparison, not a new multi-repeat throughput campaign.

Validation of the cache follow-up: 755 CPU tests passed (39 skipped), 12 focused cache/graph tests passed with CUDA available, and two consecutive real compiled MTP requests produced identical greedy output. The two-request MTP run peaked at 23528 MiB reserved with the same 64k context. Those MTP figures are an execution/memory check, not a throughput benchmark.
