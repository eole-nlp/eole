DFlash2 decoding

DFlash2 runs the BF16 incoai/Qwen3.8-27B-DFlash2 drafter with a converted Qwen3.8-27B target. It supports single-GPU, batch-one, text-only greedy inference. The seven-token proposal is verified in one eight-token target pass, using Eole's existing attention/GDN state commit and rollback.

The drafter shares the target's embeddings and vocabulary projection. Its five-layer backbone uses PyTorch SDPA. Compile mode 0 replays the complete proposal block through one CUDA graph, prepared during model loading. Fixed context K/V buffers retain only committed target states; speculative noise K/V is temporary. Target verification uses the existing compile/CUDA graph path. Intermediate target features and drafter context are bounded by its 2,048-token sliding window. Chunked prefill is supported; persistent prefix reuse is disabled for this path because existing prefix entries do not contain intermediate features.

Try locally​

Use the normal Eole environment and a converted target checkpoint. Download the separate HF-format drafter without converting it:

hf download incoai/Qwen3.8-27B-DFlash2 \
  --revision 015e795645c74b1a0eeef3b570031fb62e769bc5 \
  --include config.json model.safetensors \
  --local-dir /path/to/Qwen3.8-27B-DFlash2

EOLE_TORCH_COMPILE=1 EOLE_COMPILE_MODE=0 \
python recipes/qwen38/dflash2.py \
  --model /path/to/Qwen3.8-27B-INT4 \
  --drafter /path/to/Qwen3.8-27B-DFlash2 \
  --mode dflash2 --max-tokens 512 --repeats 2

Use --mode none and --mode mtp for controls with the same target and prompt. The recipe defaults to native BF16 vocabulary heads, a 4,096-token target cache, and fused projections. --context-length and --prompt can be adjusted.

In a regular PredictConfig, set:

dflash2_model: /path/to/Qwen3.8-27B-DFlash2
batch_size: 1
beam_size: 1
top_k: 1
compute_dtype: bf16
gpu_ranks: [0]

dflash2_model enables the external drafter and derives the proposal length from its checkpoint. self_speculative_num_tokens continues to control native MTP. This implementation has no workspace selector or deployment-template integration yet.

There are two independent quantization settings:

  • dflash2_quantization: none keeps BF16 drafter projections; int8 uses group-32 runtime RTN Marlin projections. Norms, convolution controls and the selector stay native.
  • vocabulary_quantization: none, int8 or int4 controls the shared vocabulary projection used by both the target and drafter. This changes target logits as well as proposals. The measured quantized heads use group size 128.

fuse_kvq and fuse_gate also pack the compatible INT8 drafter projections. BF16 drafter gate/up packing is an experiment, not enabled by those flags in this PR. The default HF checkpoint block size is 8, giving seven proposals. The graph path uses the checkpoint block size; self_speculative_num_tokens does not override it.

Matched benchmark: INT8 vocabulary heads​

All rows below use the same converted RedHat Qwen3.8-27B INT4 target and shared INT8 group-128 vocabulary head. This is the configuration of the original optimization table, not the INT4-head configuration used in the local Orwell script. DFlash2 uses block size 8 (seven proposals); native MTP uses three proposals.

RTX 5090; Torch 2.14.1/CUDA 13.2; Triton 3.8.0; FLA 0.6.0; FlashAttention 2.8.3. The code, English mystery and Chinese-to-English prompts are the same mtp-sampling-fixtures.json fixtures throughout. Batch one, greedy, thinking disabled, context capacity 64,000, output cap 2,048, BF16 KV cache, prefix reuse off, fused target projections and compile mode 0. Each fixture gets a 128-token warmup and three measured repetitions. Optional phase-event profiling is off. Values are median decode tokens/s, excluding the first token, prefill and warmup.

The current BF16 graph baseline reproduces all nine original output token sequences. Its original measurement was 223.0 / 139.7 / 212.6 tokens/s; the small rerun difference is measurement variation, not an implementation improvement.

Both DFlash2 rows are implemented by this PR; ordinary decoding and native MTP are matched controls. Target verification is compiled and graph-replayed in the speculative cases. The drafter graph records eager kernels; it does not itself use torch.compile.

Compilation and kernel substitutions can change rounding, proposal acceptance and generated sequences. These are observed end-to-end results, not isolated kernel speedups. No quality evaluation was performed.

Why the other tables had different numbers​

The following are graph-only BF16 drafter baselines, not successive optimization stages. Only the shared head setting and/or checkpoint block size changes:

Switching INT8 to INT4 heads at block size 8 changes acceptance from 55.3% / 29.7% / 51.6% to 67.3% / 25.7% / 43.3%, respectively. Translation length changes from 719 to 1,065 generated tokens. The 272.4 code figure is therefore not a further optimization gain over 223.0. Head projection cost and output/acceptance changes both contribute. A shorter translation is not evidence of better quality.

The block-size-4 runs use a temporary four-position drafter configuration with three proposals; block size 8 proposes seven. Longer blocks help when later proposals are accepted often enough to offset verification cost. These fixtures do not establish one universally optimal block size.

Packing and startup​

With INT8 drafter projections, fuse_kvq packs noise Q/K/V and context K/V; fuse_gate packs MLP gate/up. Original projections are released after replacement. Context K/V needs separate Marlin packing, adding about 55 MB compared with the unpacked INT8 drafter. BF16 drafter projection packing is not enabled.

Drafter graph preparation is about one second. This is startup work, separate from target-verifier compilation (about a minute cold in these tests, or a few seconds to load a saved verifier). Warmup is excluded from the throughput tables.

Supported scope and numerical behaviour​

The small-model drafter calculation was compared with the upstream reference across cache updates and sliding-window eviction (maximum FP32 difference 3e-8). Tests cover split-half RoPE, dynamic convolution, selector transitions, bounded context, chunked feature collection, real CUDA graph replay, ring wraparound, partial appends, stable-buffer request resets, packed projections, and target verification with ordinary and GDN decoders, including incorrect proposals.

Target FP32 normalization is unchanged. Drafter Q/K normalization remains FP32 and preserves intermediate BF16 casts. Reduction ordering can still affect rounding, acceptance and later trajectories. Repeated runs are deterministic within each tested configuration, but bit-identical output to single-token ordinary decoding has not been established. The tables measure throughput, not task quality; they do not establish a quality gain or loss.

DFlash2 supports single-GPU, batch-one, beam-one, text-only greedy inference. Sampling, tensor parallelism, vision inputs and other compile modes remain outside its tested scope.

The adapted drafter implementation retains the upstream MIT notice in licenses/dflash-MIT.txt.

Unsupported requests are rejected explicitly rather than falling back with the external drafter still loaded. Disable dflash2_model for sampling, multiple sequences/hypotheses, image inputs, attention output, target prefixes or decode constraints. The normal native-MTP fallback behaviour is unchanged.
